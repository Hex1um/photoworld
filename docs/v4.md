# v4：多图 / 视频 → 世界

> 状态：**管线 + 前端上传 + 两种世界表示都已打通**（2026-11-19；v4.1.1 修了高度场与上传链路的实错）。
> 质量门会拦不合格素材；素材好时能出世界，素材差时它会直接告诉你重拍。

## 一句话

v3 是"一张照片 + 扩散外推"，转身之后没有真实信息；v4 是"多张照片/一段视频 → 多视图三角化"，
每一面都真的被看见过，所以转身、绕行才成立。

## 用法

```bash
# 1) 只评估（先看能不能用，不出世界）
python pipeline/v4/build.py --input 我的照片目录 --qc-only

# 2) 评估 + 出世界
python pipeline/v4/build.py --input 视频.mp4 --out out/v4/worlds/myscene

# 3) 判定 FAIL 时强行出（不推荐，只用于调试）
python pipeline/v4/build.py --input ... --force
```

产物：`out/v4/worlds/<name>/qc.md`、`qc.json`、`world-v4.glb`（可直接用
`?glb=out/v4/worlds/<name>/world-v4.glb` 在查看器里打开）。

## 拍法建议（决定成败的不是代码，是素材）

| 要 | 不要 |
|---|---|
| 走动拍：相邻两张位移 ≥ 场景深度的 5% | 原地转圈（没有基线，三角化必崩） |
| 相邻两张重叠 1/3 以上 | 每张只挨着一点点 |
| 环绕主体 180°~360° | 只拍一面 |
| 主体有纹理（树、石头、砖墙） | 大片纯色天空/白墙 |
| 关闭电子防抖、慢一点走 | 快速甩镜（运动模糊毁匹配） |

建议：6~20 张（或 5~15 秒视频按 1.5fps 抽帧）。

## 质量门（`pipeline/v4/qc.py`）

| 指标 | PASS | WARN 下限 | FAIL 硬门槛 | 含义 / 差的时候怎么办 |
|---|---|---|---|---|
| 定位率 | ≥ 0.7 | ≥ 0.5 | < 0.4 | 有多少帧求出了位姿；低 → 加重叠 |
| 视差中位 | ≥ 1.0° | ≥ 0.5° | < 0.5° | 三角化质量；低 → **没有基线**，走动或靠近主体 |
| 重投影 RMSE | ≤ 3 px | ≤ 4.5 px | > 6 px | 镜头畸变/运动模糊；高 → 关防抖、慢走 |
| 稀疏点 | ≥ 100 | ≥ 100 | < 100 | 太少说明主体纹理不足或重叠不够 |
| 高度场填充率 | ≥ 0.08 | ≥ 0.03 | < 0.03 | 环绕是否完整；低 → 补拍背面 |

视差中位取**所有可解配对**（包含视差为 0 的配对），不是只在"有视差"的配对里取——
否则 15 组里只要 1 组有 5° 就会报 5°，把没有基线的素材捧成 PASS。

判定：PASS / WARN（能出但会有洞）/ FAIL（直接报"重拍"，除非 `--force`）。
**FAIL 默认不出世界**，且"建完才发现填充率不达标"的情况会把 GLB 删掉，避免半成品流到下游。
v4.1.2 起，视差 < 0.5° 或点数 < 100 也是硬 FAIL：此前纯旋转素材因 RMSE 很小被判
WARN 放行，与本文口径矛盾。

v4.1.3 修正填充率门槛：fill = 有数据格子 / cells²，cells 默认 200（4 万格），而 SfM
只有一两万个稀疏点，**数学上填不满一半**。旧门槛 0.2/0.5 导致合格素材建完 GLB 后
立刻被判 FAIL 并删掉（端到端实测复现）。按对照素材实测定为 0.03/0.08：完整绕拍
fill≈0.10，只拍 18° 窄带 fill≈0.018。同时高度场范围改用 2/98 分位裁剪三角化离群点，
不再让个别 x=60 的点把 span 从 1 拉到 120。

端到端自测（造一段有基线的走动素材，验证 PASS 真的能出 GLB）：

```bash
python tools/make_synthetic_v4.py --out out/_selftest_good
python pipeline/v4/build.py --input out/_selftest_good --out out/_selftest_world
python tools/test_v413_fixes.py
```

仓库自带的 `testdata/v4_*` 全是纯旋转 / 远景素材，按现行判据应全部 FAIL；它们验证的是
「坏素材被拦住」，上面这个生成器补的是「好素材能出图」的另一半。

## 实测（合成集，用于验证管线行为）

| 输入 | 定位 | 视差 | RMSE | 点 | 判定 | 说明 |
|---|---|---|---|---|---|---|
| `testdata/v4_alpine`（9 帧原地转） | 9/9 | 0.38° | 1.91px | 6251 | **FAIL** | 定位满格、RMSE 小，但基线不足 → 旧版误判 WARN |
| `testdata/v4_terrain`（绕原地转 20° 步进，纯地形） | 4/7 | 0.19° | 1.40px | 1427 | **FAIL** | 纯旋转没有基线 → 这正是 QC 该拦的 |
| `testdata/v4_walk`（前走 0.35m×5，远景） | 2/6 | 0.00° | 0.09px | 0 | **FAIL** | 场景太远，0.35m 位移产生的视差 < 0.1° |

结论：**QC 的判断是对的** —— 这两组素材本来就不该重建。真实拍摄（走近一个人/一栋房子、
或绕着房间走）视差会到 5~20°，那时才谈得上出好世界。

## 已知限制

1. **内参未知**：`f = 1.2 × max(w,h)`（`--focal-ratio` 可调）。手机广角/长焦差异会让尺度偏差。
2. **尺度不可观**：输出是"任意单位"，不做绝对米制标定（要对米制得靠 IMU 或已知尺寸物）。
3. **垂直面仍不稳**：`--mesh tsdf` 能出墙/树干，但对位姿与深度要求高；素材一般时默认
   高度场更稳（v4.1.1 修了空体素取色导致的黑面，但没有改变"素材决定上限"这一事实）。
4. **不做闭环平差**：绕一圈首尾衔接处会有累积漂移（QC 不报，但能看出来）。
5. **本机计算依赖**：SfM 在命令行服务里跑，页面只负责上传与轮询；`numpy/opencv-python/
   scipy/pillow` 缺一不可，缺依赖时面板会给出明确指令，不再误报成素材问题。

## 下一步（按性价比排）

1. **闭环平差 / 位姿精化**：当前绕一圈会累积漂移，直接影响 TSDF 与填充率；
2. **TSDF 质量**：用更好的单目深度或稠密匹配替代"稀疏点线性对齐"，减少黑面与糊团；
3. **视频 → 3DGS**（`gsplat`）：8GB 上用低分辨率小场景可试，是"能走能转身"的终极形态。

## ② 垂直面（TSDF + marching cubes）⚠️ 已实现，默认关闭

`pipeline/v4/tsdf.py`：每帧单目深度按 SfM 稀疏点做线性对齐（`1/z = a·disp + b`）→
反投影进体素 → 占据率当隐式场 → `skimage.measure.marching_cubes` → 带顶点色的网格。

已经做的健壮性：

* 深度对齐退化（`a ≤ 0`，即"视差越大反而越远"）时**跳过该帧**，否则会把体素糊成一团；
* 体素总数上限 8M，超了自动放大体素；
* 输出统一缩放到"跨度 40 单位、脚下贴地、放在相机前方"——否则查看器会站在模型内部，
  表现为一片空白（这一步翻车过两次）。

**现状**：在合成素材（4 帧、视差 0.25°）上会出大块黑面 —— 深度与位姿都不够好。
真实素材（视差 5~20°、十几帧）才有意义。所以 `--mesh` 默认仍是 `heightfield`。
v4.1.1 修掉了其中一类确定性的黑面：等值面顶点落在空体素时旧版取到纯黑，现在取最近
命中体素的颜色；剩下的黑面仍是素材/深度质量问题。

# COLMAP 接入（2026-11-21，解决"位姿不准"）

## 为什么要接

自测结论（`testdata/lego`，26 张绕物体 360°、带真值）：

| 位姿来源 | 定位 | 光度一致性 | 相机半径 | 世界 |
|---|---|---|---|---|
| 手写 SfM | 26/26 | 0.148 | 10.3/13.0/8.5（真值恒 4.03） | 碎片 |
| **COLMAP** | 26/26 | **0.059** | 与真值同形（差一个整体尺度） | **能认出是那台乐高推土机** |

重投影 RMSE 在两种情况下都很小（0.86 / 0），**只有光度一致性分得开** ——
这是"位姿整体错位"的唯一可靠信号。

## 安装（一次性）

```bash
# 154MB，CUDA 版；解压到 tools/colmap/（bin/colmap.exe）
# 也可设 COLMAP_EXE 指向别处
```

`pipeline/v4/colmap.py` 会自动找 `tools/colmap/bin/colmap.exe` / `$COLMAP_EXE` / PATH。

## 用法

```bash
# 稀疏（快，~6s）：只求位姿 + 稀疏点
python pipeline/v4/build.py --input 照片目录 --poses colmap

# 稠密（推荐，~1min）：再跑 patch_match_stereo + stereo_fusion，得到真 MVS 点云
python pipeline/v4/build.py --input 照片目录 --poses colmap --dense --mesh tsdf
```

前端（`tools/serve_api.py`）检测到 COLMAP 时**自动加** `--poses colmap --dense`。

## 实测开销（26 张 800×800，RTX 5070 Laptop）

| 步骤 | 耗时 |
|---|---|
| 特征提取 + 匹配 + 建图 | ~5 s |
| 去畸变 + 稠密匹配 + 融合 | ~7 s（144,923 个 MVS 点）|
| TSDF 成网格 | ~50 s（110 万顶点）|

## 仍然不足的

* **网格质量**：TSDF-lite 用占据率 + marching cubes，表面是"薄壳"，
  边缘毛糙、有洞。要干净需要 Poisson / screened Poisson 重建（Open3D）。
* **尺度**：COLMAP 的尺度是任意的（第一对基线为 1），要绝对米制得靠 IMU 或已知尺寸物。
* 命令行默认仍是 `--poses ours`（避免"装了 COLMAP 就悄悄改变历史结果"），
  只有显式指定或走前端服务时才用 COLMAP。

# 世界表示：三条路各自适合什么（实测）

| 表示 | 适合 | 局限 | 实测（lego，14 万 MVS 点）|
|---|---|---|---|
| `--mesh heightfield` | 地形/风景（有明确"地面"） | 没有垂直面 | 稳定，快 |
| `--mesh tsdf` | 物体、室内 | 是"薄壳"，边缘毛、有洞 | **能认出推土机**（`shots/v4_colmap_lego.png`）|
| `--mesh poisson` | 理论上最干净 | 对法线朝向极敏感 | **拉丝面条**，不可用 |

泊松为什么失败：COLMAP `stereo_fusion` 的法线只在每个参考视图内自洽、整体不是全局
一致朝向；泊松在正反之间来回就出碎片。要做对需要"全局法线一致化"（用位姿做可见性投票）。
