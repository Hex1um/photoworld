# 18 图 × 32 机位 目检（v2.15.23）："不连续"到底是什么

采集：2026-11-17 15:28，`tools/multiview.mjs --views 32`，Edge + D3D11，960×600，
18 张语料（`corpus_test` 9 张 + `corpus_acc` 前 9 张），耗时 12 分 29 秒，0 失败。
联系表：`tools/montage_views.py`（6 机位：A00 正面 / A03 / A06 / A09 侧背 / B18 远 / C28 照片外）。

## 0. 先说一个必须先纠正的前提（这轮最重要的发现）

`?img=` 与 `?w=` 两个入口，**实际渲染的不是 `js/world.js` 的浏览器重建**，
而是 **v2 服务端（`server/app.py` @ 127.0.0.1:8100）烘焙出来的 6 层 GLB**
（`near / backdrop / solid / ground / top / topHole`，本图 937,228 三角、29.5MB）。
证据：`document.body.dataset.mode === "asset"`，HUD 显示 `V2 · 6 层`，
接口直调 `POST /api/reconstruct` 返回同样的层名。

这件事的后果很直接：

- **v2.15.11 ~ v2.15.21 里对 `js/world.js` 的改动（薄壳淡出、地面交棒、断口补片、
  地面点云平铺 UV）都不会作用在语料图上** —— 那几轮"指标不动"不是巧合，
  而是根本没有执行到。只有内置世界在服务不可用时才会走那条路径。
- 那个服务**一直在跑**，并且**模型常驻显存**：用户删掉 `models/da2_large`
  之后它照样能出图（进程内权重还在）。所以"删了权重却还在出图"不是灵异事件。
  权重已按 `pipeline/v2/README.md` 用 hf-mirror 重新下回（1.25GB，
  `api.available() == {'ok': True}`）。

## 2. 目检：不连续分成四类（按出现频率）

### A. 大平板 + 照片小贴片（**最普遍**，18 张里 15 张）

代表：`06_boat_beach`（6 机位联系表）。正面 A00 是照片里的船，还算完整；A02/A03 起，
画面 80% 是一整块**没有纹理的浅色平板**，照片内容缩成一小块悬在中间。

原因在渲染端，很清楚：`js/renderer.js` 画 `top/topHole` 时是

```js
drawMesh(world, groundMeshNow, { tex: null, mode: GROUND_MODE, ... });
```

也就是**纯顶点色、不用贴图**。而 `pipeline/v2/ldi.py` 的 `build_top_skin`
（§"UV：把照片里的地面区域当作可平铺纹理"）明明烘焙了"照片地面 bbox 内平铺"的 UV ——
**这份 UV 从来没被用过**。于是沙滩、草地、水面、雪地都是同一块塑料板。

A/B 实测（`?gtex=1` 用照片贴图 + mode 6）：

| | voidFrac | innerVoid | lowVoid | detail |
|---|---|---|---|---|
| 现状（顶点色） | 0.0268 | 0.0314 | 0.0597 | 0.0150 |
| 照片贴图 | **0.1211** | **0.1158** | **0.2860** | 0.0195 |

**更差**：UV 平铺把"海面"也铺到整片地上，成了蓝条纹。结论：**不能直接把照片当地面贴图**，
必须要么由 ldi 烘一张"只含地面色"的低频贴图（把水面/天空/天空反射排除），
要么把顶点色改成逐区域的真实地面色（现在全图只取一个 75 分位色）。

### B. 地面上的放射状拉丝（**同源**，18 张全有）

从相机脚下沿视线炸开的条纹。之前几轮把它归因到"壳层地面 UV"，
在 `js/world.js` 里改了两版（`galpha`、`gpts`）都没效果 —— 现在知道原因：
**这段几何来自 v2 的 `near`/`ground` 层，不在浏览器构建器里**。
`?gpts=1` 的对照截图（地面变灰绿板、与照片带之间出硬边）保留在代码里，
但**默认关**，等 v2 侧方案定了再启用。

### C. 壳层撕裂 / 悬浮条带（约 8 张）

代表：`04_coast_cliff`、`05_canyon_strata`、`09_lamppost`、`2c3ecda9`。
表现：照片内容被撕成一条条竖直长条，或者变成悬空的板；转身 90° 后最明显。
机制在 `pipeline/v2/ldi.py` 的 `cap_depth_gradient` + `cliff_mask` + 层间剔除，
与浏览器侧的 `edgeRatio` 那套逻辑是两套独立实现。

### D. 室内 / 单色图的指标失效（不是渲染问题）

`0116beac`（黑白雪山）`voidFrac 0.530 / lowVoid 0.932`：画面内容还在，
但整幅深灰阶，`voidFrac` 的"接近清屏色"判据把它全判成空底。
这条已在 `docs/ISSUES.md §23` 记过，仍然成立。

## 3. 这一轮做了什么（都带开关，可回退）

| 改动 | 开关 | 状态 |
|---|---|---|
| 图层逐个摘除取证 | `?hide=near,backdrop,solid,ground,top,topHole` | **新增，保留** |
| 地面层改用照片贴图 | `?gtex=1` | 默认关（实测更差） |
| 地面点云平铺 UV | `?gpts=1` | 默认关（实测地面变灰板） |
| 壳层地面距离交棒 | `?galpha=11,30,1` | 默认关（未在真实链路上验证） |
| 断口补片（剔除四边形压扁后填回） | `?fill=1` | 默认关（同上） |

`?hide=` 是本轮最实用的产出：在此之前，判断"这条 artifact 是哪一层画的"
只能靠猜（`?skip=` 那套是浏览器构建器的层名，对 GLB 层无效）。

## 4. 下一步（按"能不能一次验收"排序）

1. **地面层要有真实地面色**（解决 A）：在 `ldi.py` 的 `build_top_skin` 里把
   `base_c` 从"全图一个 75 分位色"改成**逐格采样照片地面像素的颜色场**（带空洞填充），
   水面/天空像素排除。验收：`06_boat_beach` 的 C 圈不再是塑料板，
   同时 `voidFrac` 不升高（照片贴图那条路已经证明"整片平铺"不行）。
2. **v2 侧的地面拉丝**（解决 B）：`near` 层的地面像素应该**不参与**照片 UV 采样，
   改为与 `ground` 层同材质，并把 `ground` 层铺到照片足迹里（`hole_mask` 现在
   故意挖空，正是拉丝露出来的地方）。验收：`02_lake_pier` / `04_coast_cliff`
   的 A 圈地面无放射条纹，且 C 圈没有新增空洞。
3. **壳层撕裂**（解决 C）：`cap_depth_gradient` 的 k 与 `cliff_mask` 的阈值是
   硬编码的经验值，应当按"单图深度分位"自适应；并用 `?hide=` 逐层确认撕裂
   归 `near` 还是 `solid`（本轮 A/B 显示 `04_coast_cliff` 的巨板在 `solid` 层仍在）。

> 教训补充（写给下一轮）：**改渲染/几何之前先确认当前跑的是哪条链路**。
> `?img=` 默认走 v2 服务端，浏览器构建器只在服务不可用时接管；
> 两者层名、参数、剔除规则都不同，A/B 必须两边分别说清楚。
